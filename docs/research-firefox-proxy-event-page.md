# Firefox proxy event-page findings

Checked 2026-11-09 against Mozilla documentation and current `mozilla/gecko-dev` source.

## Findings

- **Asynchronous registration is not reliable for event-page persistence.** Firefox's background-script guidance says event listeners must be registered synchronously from the start of the page; listeners registered asynchronously are not properly triggered. `permissions.contains()` returns a Promise, so registering `proxy.onRequest` only in its continuation can miss the event-page startup registration window. Gecko's `EventManager` documents that synchronous background-context listeners are persisted and records a new listener only while `context.listenerPromises` is present. Treat the pattern as capable of failing to persist/wake, rather than claiming every async registration always fails. ([MDN: Background scripts](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/Background_scripts#add_listeners), [MDN: `permissions.contains()`](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/API/permissions/contains#return_value), [Gecko `ExtensionCommon.sys.mjs`](https://github.com/mozilla/gecko-dev/blob/master/toolkit/components/extensions/ExtensionCommon.sys.mjs#L2255-L2267) and [listener recording](https://github.com/mozilla/gecko-dev/blob/master/toolkit/components/extensions/ExtensionCommon.sys.mjs#L2844-L2924))

- **`proxy.onRequest` itself supports persistent registration, subject to that startup timing.** Gecko implements `proxy` as an `ExtensionAPIPersistent` API and puts `onRequest` in `PERSISTENT_EVENTS`. ([Gecko `ext-proxy.js`](https://github.com/mozilla/gecko-dev/blob/master/toolkit/components/extensions/parent/ext-proxy.js#L144-L150))

- **An unconditional top-level `browser.proxy` access is unsafe when `proxy` is optional and not granted.** Firefox's proxy schema marks the namespace as requiring the `proxy` permission and permits `proxy` as an optional permission. Gecko's API loader rejects loading a module when none of its required permissions are granted. Guard access until the permission is granted; do not assume the namespace exists before then. ([Gecko `proxy.json`](https://github.com/mozilla/gecko-dev/blob/master/toolkit/components/extensions/schemas/proxy.json#L1-L20), [Gecko permission gate](https://github.com/mozilla/gecko-dev/blob/master/toolkit/components/extensions/ExtensionCommon.sys.mjs#L1779-L1792), [MDN: `proxy.onRequest` permission requirements](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/API/proxy/onRequest#permissions))

## Isolated runtime check

Use `web-ext run` with its default profile behavior: Mozilla documents that it creates a fresh temporary Firefox profile and discards it when the command ends. Do not pass a real profile path. In that disposable profile, temporarily load the extension, close any background-page inspector or other open extension view, and let the non-persistent background page become idle. Then navigate to a URL covered by the proxy listener's filter and host permission; observe whether the listener wakes and handles the request. Firefox documents that an open view prevents the background page from closing, so leave the inspector closed. ([Mozilla Extension Workshop: `web-ext run`](https://extensionworkshop.com/documentation/develop/getting-started-with-web-ext/), [MDN: Background scripts](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/Background_scripts))

For a deliberate restart check in that same disposable profile, navigate to `about:crashextensions`; MDN documents that it silently crashes the extension process. Firefox then restarts a non-persistent background script when it dispatches one of the extension's API event listeners. This exercises crash recovery, which is distinct from natural idle shutdown. ([MDN: Background scripts](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/Background_scripts))

**Runtime evidence:** Firefox Developer Edition 160 reproduces the 0.2.2 failure and verifies 0.2.3 recovery in [the matched-filter comparison](evals/0.2.3/firefox-wake-filter-comparison.json). Both disposable profiles use `http://wake-fixture.invalid/*`, pre-granted proxy permission and a script-free observation page. Both observe a stopped background before the first selected request. The 0.2.2 request fails with `NS_ERROR_UNKNOWN_HOST`; 0.2.3 receives the local proxy response and confirms the background has restarted. The copied 0.2.2 runner changes only the expected registration-site count from two to one, matching the older source, and uses the older package version. Runtime assertions are unchanged. The original [before](evals/0.2.3/firefox-wake-before.json) used the unrestricted filter; the original [after](evals/0.2.3/firefox-wake-output.json) used the narrowed filter, so those initial records alone were not a matched-filter comparison. The release filter remains `<all_urls>`. This verifies forced crash recovery on the tested Firefox build, not natural idle shutdown, the optional permission dialog or every supported Firefox release.
